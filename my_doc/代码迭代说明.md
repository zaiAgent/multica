## 2. 前端链路（AR-01~03：审批描述直白化）

### 2.1 审批卡片三层结构（四端中的三端）

PlainBriefCard 在三处渲染，同一解析器：

1. **交接确认卡**（`handoff-confirm-dialog.tsx`）：brief 区从"折叠按钮+原始文本"升级为三层卡片——人此刻要判断放行，先看结论与风险，再看放行后动作，需要时展开原文；
2. **时间线交接条目**（`timeline-handoff.tsx`）：handoff_note 以 compact 三层卡片渲染，结论层直接可见；
3. **时间线审核结论行**（同文件 TimelineVerdict）：`[有条件通过] 需要人工检查、证据不足 · 备注一句话` 单行挂接。

（Run 详情页的 brief 预览沿用 BriefPreviewDialog 的原始视图——那里是给**配置者**看的原文，不是审核时刻，保持不变是有意为之。）

### 2.2 术语翻译表与风险标签

- 术语表 18 条，最长匹配优先（`git push --force` 归 force_push 而非 push_remote）；渲染为 `npm publish → 发布到公网` chip，**不篡改原文**；
- 风险标签 4 族：数据丢失/不可逆（高·红）、影响外部环境（中·琥珀）、从网络读取（低·灰）；
- 匹配纪律：词边界锚定（`deployed` 叙述不触发 deploy）；`--force-with-lease` 是安全形式不触发高危；
- 解析器防御性降级：无结构文本 → 仅结论层+证据层，绝不臆造中间层。

## 3. 审核链路（AR-04~06：人工审核结论）

### 3.1 触发时机

离开 `in_review` 列的状态变更（in_review→done 本无交接确认，现在也会弹卡）——这是 Multica 里真正的"审核时刻"。结论默认 **pass**（一次确认即完成），换 reject/conditional_pass 展开理由与备注。

### 3.2 数据流

```
确认卡(ReviewVerdictInput)
  → onConfirm({ reviewVerdict, reviewReasons, reviewNote })
  → 4 个调用方把 review_verdict / review_reasons(逗号连) / review_note 并入更新请求
  → POST /api/issues/:id（或 /move，白名单已放行三字段）
  → server 校验 validateReviewVerdict + 仅 member + 仅 from=in_review + 仅 statusChanged
  → issue:updated 事件携带三字段
  → activity_listeners 写入 status_changed 时间线条目 details
  → 前端 timeline 渲染 TimelineVerdict（chip + 理由本地化 + 备注）
```

### 3.3 服务器端纪律（防滥用）

- 结论三值之外的任何值 → 400；
- 理由/备注不得脱离结论单独出现 → 400；
- **agent 不得代书结论**（actorType=agent 时字段被忽略）；
- 非 in_review 出发的变更忽略该字段（旧客户端不能乱盖结论）；
- **批更新拒绝**该字段（一份结论属于一次审核）——与 duplicate_of_issue_id 同样的拒绝模式。

### 3.4 前端缓存纪律

三个字段是**写时控制字段**（control fields）：在 `useUpdateIssue`/`useBatchUpdateIssues` 的乐观更新里与 `suppress_run` 等一起剥离，绝不进入 Issue 缓存补丁（`mutations.ts` 三处剥离点全部补齐）。

## 8. 设计不变量（本次迭代遵守）

1. **叠加不替换**：approved/rejected 原语义原样保留，ReviewVerdict 是新增层；未发送结论的更新行为与旧版完全一致；
2. **写时字段不落库**：三个字段只进事件与时间线 details，不进 issue 表，无 schema 迁移；
3. **旧客户端零破坏**：不认识新字段的老客户端不发送它们，一切照旧；
4. **本地化在渲染层**：存储的是 key，翻译不进数据；
5. **一份结论属于一次审核**：批更新拒绝，agent 不可代书。
