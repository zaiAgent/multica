# Multica 审核改进计划：审批描述直白化 + 人工审核结论

> 目标：让人的审核从"读天书"变成"30 秒可判断"。
> 三原则：**叠加不替换、开关灰度、不破坏现状**（approved/rejected 原语义原样保留）。
> 登记项 AR-01~AR-08，共 40 人日，三期 16+14+10。

## 1. 现状问题：审批描述为什么难读

Multica 的审核时刻 = 智能体在列内完成目标、提交交付、人把 Issue 从「待审核」列拖走的瞬间。人此刻要读的是：

1. 智能体提交的交付说明（评论形式，术语密度高）；
2. 工作流简报（handoff brief，服务端渲染，英文，含 `multica issue status` 命令行）；
3. Run 时间线与代码改动。

三个问题：**术语不翻译**（bash.exec、npm publish、git push --force 对非工程读者是天书）；**结构不对齐决策**（人要判断的是"放不放行"，卡片给的是"它做了什么"的流水账）；**结论无处安放**（人审完只有"移动列"这一个动作，审核结论本身没有落点，无法复盘）。

## 2. 方案总览：三层卡片 + 一个结论

- **AR-01~03（P0）**：审批卡片三层结构 + 术语翻译表 + 风险标签——解决"读得懂"；
- **AR-04~06（P1）**：人工审核结论 ReviewVerdict（pass/reject/conditional-pass）+ 勾选式理由 + 结论三去向——解决"结论有落点"；
- **AR-07~08（P2）**：驳回理由 TOP 榜复盘视图 + 结论驱动流程反哺——解决"越审越准"。

## 3. AR-01 审批卡片三层结构（P0）

**结论层**（默认展开，一眼）：
- 一句话结论（headline）；
- 风险标签行（见 AR-03）。

**决策层**（默认展开，五要素对齐人的判断）：

| 字段 | 回答的问题 | 示例 |
|---|---|---|
| 步骤 steps | 它做了什么 | ①跑测试 ②发布包 ③提交 PR |
| 影响 impact | 动了哪些东西 | 修改 12 个文件，含 2 个配置 |
| 花费 cost | 代价多少 | 本轮约 0.8 美元（预算余量 73%） |
| 风险 risk | 哪里可能出事 | 见风险标签 |
| 你要判断 question | 人此刻必须回答的 | 是否允许发布到公网？ |

**证据层**（默认折叠，一键展开）：原始说明全文，逐字未改。

**四端渲染**：时间线条目 / 看板列交接确认卡 / Run 详情页 / 飞书消息卡片——同一解析器（plain-brief），四处复用。

## 4. AR-02 术语翻译表（P0）

人话字段**强制校验**：智能体提交审批时，结构化字段缺结论句直接打回重填。

术语表（节选，完整表在代码 `plain-brief.ts` 的 GLOSSARY_PATTERNS，18 条）：

| 术语 | 人话 |
|---|---|
| bash / sh -c | 运行命令 |
| npm install | 安装依赖包 |
| **npm publish** | **发布到公网** |
| git push | 推送到远端仓库 |
| **git push --force** | **强制覆盖远端历史** |
| git reset --hard | 丢弃本地改动 |
| rm -rf | 删除文件（递归） |
| docker | 运行容器 |
| kubectl | 部署到集群 |
| curl / wget | 从网络下载 |
| secrets / .env / token | 涉及密钥 |
| migration | 执行数据库迁移 |
| PR | 发起合并请求 |

匹配规则：最长匹配优先（git push --force 归入 force_push 而非 push_remote）；渲染时"术语 → 人话"chip 并列展示，不篡改原文。

## 5. AR-03 风险标签分级（P0）

| 级别 | 标签 | 触发词族 |
|---|---|---|
| 高 | 数据丢失 | rm -rf、DROP TABLE、truncate、git clean |
| 高 | 不可逆 | push --force、reset --hard、sudo、chmod -R |
| 中 | 影响外部环境 | npm publish、docker push、git push、kubectl、deploy |
| 低 | 从网络读取 | curl、wget、http(s) |

匹配规则：词边界锚定（"deployed"是叙述不触发 deploy）；`--force-with-lease` 是安全的 force 形式，不触发高危。渲染：高危红、中危琥珀、低危灰。

## 6. AR-04 人工审核结论 ReviewVerdict（P1）

```ts
verdict: "pass" | "reject" | "conditional_pass"
reasons: ("goal_met" | "quality_below_bar" | "scope_crept"
        | "risk_not_worth_it" | "needs_human_check"
        | "incomplete_evidence")[]
note: string  // 一句话理由 / 有条件通过的条件
```

**语义**：
- **pass**：达标放行；
- **reject**：驳回原列，理由随行；
- **conditional-pass**：带条件放行——**条件自动转待办 Issue，闭环前本 Issue 不可关**。

**写入纪律**：写后不可改，随时间线条目入审计（未来并入 AuditLedger 哈希链，见 NG-D）；仅人（member）可写，智能体不得代书。

**落点**（Multica 代码映射）：`UpdateIssueRequest` 增加 `review_verdict`/`review_reasons`/`review_note` 三个写时字段，仅在**离开 in_review 列的状态变更**时随事件写入时间线 `status_changed` 条目的 details；批更新拒绝该字段（一份结论属于一次审核）。

## 7. AR-05 勾选式理由短语库（P1）

六条理由 chip，3 击完成一次驳回（选结论 → 勾理由 → 确认）：达成目标 / 质量未达标 / 超出范围 / 风险不值得 / 需人工检查 / 证据不足。理由以 key 存储（`quality_below_bar`），渲染时本地化——不把翻译烧进数据。

## 8. AR-06 结论三去向（P1）

1. **时间线单行**：`[通过] 达成目标 · 备注一句话` 挂在状态变更条目下；
2. **账本**：随 activity details 落库，可查询；
3. **复盘**：见 AR-07。

## 9. AR-07/AR-08（P2）

- **AR-07 驳回理由 TOP 榜**：按智能体/工作流聚合驳回理由分布，暴露"谁总在哪个环节翻车"；
- **AR-08 结论驱动流程反哺**：驳回率高的列自动提示加长 instructions 或插入前置检查步骤。

## 10. 审批文案五军规

1. **一句话先行**：结论层永远在第一行；
2. **一卡一问**：一张卡片只问一个"你要判断"；
3. **数字带语境**：金额必带预算余量百分比；
4. **风险独立成行**：不与普通信息混排；
5. **技术细节折叠**：证据层默认收起。

## 11. 登记与排期

| 期 | 项 | 人日 |
|---|---|---|
| 一期 | AR-01 卡片三层 + AR-02 术语表 + AR-03 风险标签 | 16 |
| 二期 | AR-04 ReviewVerdict + AR-05 理由短语 + AR-06 三去向 | 14 |
| 三期 | AR-07 TOP 榜 + AR-08 反哺 | 10 |
| 合计 | | **40** |

## 12. 验收标准

1. **30 秒可判断**：新卡片从打开到能做出 pass/reject 判断 ≤ 30 秒（抽测）；
2. **覆盖率**：术语表对交付说明中高危/中危术语的覆盖率 ≥ 90%；
3. **误批率下降**：灰度期间驳回中被"事后发现该驳回"的比例下降（人工抽检口径）；
4. **结论闭环率**：conditional-pass 的条件待办 Issue 关闭率 ≥ 80%（三期后统计）。
