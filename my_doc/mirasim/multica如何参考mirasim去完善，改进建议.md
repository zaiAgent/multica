# Multica 参考 MiraSim 的完善与改进建议

> 定位：本文件是第 3 册《Multica改进架构设计书·Multica-NG》的**补充参考输入**——用 MiraSim 已验证的机制，细化或增补 NG-A~NG-F 六子域的设计，不推翻既有分级与路线图。
> 依据：《mirasim软件架构原理与说明.md》（官方文档快照 2026-11）与《对比两软件的差异.md》的事实底座。
> 编号约定：新增借鉴项记 **MS-01~MS-08**（MiraSim-Sourced），与 NG-A01~NG-X05 登记体系并行，可直接入看板。

## 1. 总原则

1. **借鉴机制，不借鉴形态**：学它的干预语义、熔断设计、账本口径，不把 Multica 改成 IDE 或桌面应用；
2. **延续 NG 三原则**：插件化（关掉等于没改过）、开关化（按工作区灰度）、不破坏（引用挂接不替代现有 Workflows/看板/飞书路径）；
3. **每项建议落到"痛点 → 改法 → 与 NG 衔接 → 优先级/人日"四要素**，可直接转为 issue。

## 2. 八项借鉴建议

### MS-01 成本账本：五维分摊到单次调用（P0）

- **MiraSim 机制**：流量监控把每次模型调用入账（token、缓存命中、成本估算）；分摊表按**智能体/模型/账号/工作区/会话**五维给出占比、调用次数、输入输出、缓存命中率；可下钻单次调用（推理 token、耗时、状态）；CSV 导出 + ui-cli 脚本出口。
- **Multica 痛点**：Token 消耗统计粗粒度（第 1 册只能给优化建议），NG-A 虽规划了 CostEvent 事件流与 QuotaSnapshot，但**明细维度与下钻口径未定案**。
- **建议改法**：直接采纳其五维作为 Multica 的 CostEvent 检索维度——**智能体 / 模型 / 账号（API key 归属）/ 工作区 / Run**（会话→Run 的概念映射）；补"单次调用"下钻视图与 CSV 导出。预算熔断（NG-A 三态机）不变，账本只是其观测面。
- **衔接**：细化 NG-A02/A03 的落地口径；与预算闸门共用一条事件流，一鱼两吃。
- **人日估算**：约 10 人日。

### MS-02 Run 内干预语义：steer / jump / recall（P1）

- **MiraSim 机制**：运行中会话四种动作——send（排队尾）、**steer（不打断当前轮，下一步生效并标记）**、jump（打断当前轮立即执行）、recall（取回编辑）；配置锁定原则（排队指令锁定发送时配置）。
- **Multica 痛点**：Run 入状态机后人只能等或整跑重试；Autopilot 缺少"中途给一句话"的通道；第 3 册已把"人始终在环"列为高压线，却没有具体干预协议。
- **建议改法**：在 Run 上定义同构三动作：**SteerMessage（注入当前轮，不打断工具调用，Run 状态不变）**、**InterruptJump（打断当前轮，按 Run 失败策略记录一次中断）**、**QueueRecall（撤回排队指令）**；全部记入 Issue 时间线（可审计）；steer 消息对智能体以系统注入形式出现在 transcript。
- **衔接**：NG-B 失败策略与 NG-D 审计账本的联合扩展；daemon 已有 15s 心跳通道，消息注入可复用心跳连接下发。
- **人日估算**：约 8 人日。

### MS-03 worktree-per-run：同仓库文件级并行（P1）

- **MiraSim 机制**：会话可选运行在独立分支的 Git worktree 检出中；同仓库并行智能体互不碰文件；合并即普通 Git 合并、放弃即删分支；删除会话连带删 worktree，有未提交改动时 Git 拒删（安全闸）。
- **Multica 痛点**：Squad 多智能体协作时若两 Run 改同一仓库必然冲突；现有 Workflows 无并行网关（第 3 册 NG-B 的 fan-out 收敛已规划**任务级**并行，但**文件级**隔离缺失）。
- **建议改法**：Agent/Runtime 增加可选属性 `isolation: worktree`；Run 派发时自动建自动命名 worktree（基准分支取 Issue 所在分支），结束时按 Verdict 决定合并/放弃；合并动作走既有审批门（NG-D），未提交改动拒删沿用 Git 原生行为。
- **衔接**：为 NG-B 的 fan-out/AND 收敛补上文件级底座；第 2 册 LinkLite 例程可原样重跑（不勾选 worktree 即旧行为，开关化达标）。
- **人日估算**：约 12 人日。

### MS-04 智能体间通信三重熔断 + 消息账本（P1）

- **MiraSim 机制**：会话默认隔离、@点名即互联；五工具（list/read/send/read_message/start_session）+ 投递语义表；三重熔断（频次 30 条后每 2 秒恢复 1 条 / 链深 24 跳遇真人重置 / 乒乓 5 分钟 12 条无真人输入即熔断）+ 本地 jsonl 账本 90 天。
- **Multica 痛点**：Squad 协议内智能体协作，但跨 Run/跨智能体通信无统一频控、无环路防护、无独立消息账本；一旦放开智能体互发消息，死循环风险直接落到预算上（NG-A 熔断会兜底，但代价是烧钱）。
- **建议改法**：为 Squad 协议增加同级防护三件套（数值可直接沿用：30/2s、24 跳、12 条/5 分钟）；任何智能体间消息入 AuditLedger（NG-D）并单独落消息账本文件（按月 jsonl）；乒乓熔断状态在看板可见，真人参与即重置。
- **衔接**：NG-B Squad 协议与 NG-D 账本的联合扩展；预算熔断（NG-A）之前的"低成本防线"。
- **人日估算**：约 6 人日。

### MS-05 上下文观测环 + 自动压缩（P1，含 P2 项）

- **MiraSim 机制**：发送按钮旁圆环实时显示上下文窗口占用；占满自动压缩（概括腾空间）；`/compact` 手动压缩。
- **Multica 痛点**：Run 无上下文占用可见性，长任务悄悄膨胀直至截断；NG-C 的 ContextAssembly 规划了"召回→过滤→排序→token 装箱"，但**装箱前的实时观测与自动降载**未覆盖。
- **建议改法**：Run 详情页加同款占用环（daemon 心跳里带上下文用量即可，增量极小）；达到阈值（如 80%）触发 NG-C 装箱管线的降序裁剪；手动压缩暴露为 CLI/飞书命令。
- **衔接**：NG-C 装箱管线的观测前置件；预警阈值与 NG-A 的 80% 预警口径对齐，体验统一。
- **人日估算**：观测环 3 人日（P1）；自动压缩接入装箱 5 人日（P2）。

### MS-06 模拟用户 eval：验收闭环新角色（P2）

- **MiraSim 机制**：内置 `eval` 技能——模拟用户从真实入口把成品试用一遍，截图与每步记录留在本机；配合结构化浏览器读取（读结构而非截图，社区口径传输量差约 330 倍）与真实 Chrome/模拟器驱动；官方 Research Notes 以 Generative Agents 与 Voyager 为理论依据。
- **Multica 痛点**：验收靠人工检查 + 看板流转；NG-F 规划了复合质量门（Verdict×CI×外部验收），"外部验收"一环仍是人。
- **建议改法**：在 NG-F 复合质量门中新增第四成员 **SimulatedUser**：Guardian 智能体（或独立 eval 智能体）在 Run 完成后按验收标准驱动真实浏览器/接口实测，产出结构化验收记录（每步截图+结论）挂到 Issue；浏览器驱动优先选**结构化读取**路线（无头浏览器 + DOM 提取），避免截图烧 token。
- **衔接**：NG-F 质量门的补全；Submission 契约（deliverables）中的"可实测交付物"自动触发。
- **人日估算**：约 15 人日（结构化读取简化版可压至 10）。

### MS-07 Transcript 分叉 / 重跑 / 回退（P2）

- **MiraSim 机制**：任意回复轮可作新分支起点（继承历史、原会话继续）；重跑按原配置重问一次（重跑早轮丢弃后续轮，菜单注明）；回退可选恢复对话/代码/两者，消息回填输入框。
- **Multica 痛点**：Run 失败只能整跑重试；定向返工（NG-B rework-context）有了"返工范围"，但**从某一轮分叉重试**的细粒度恢复缺失，长任务返工成本高。
- **建议改法**：Run 的 transcript 增加三个操作：**ForkFromTurn**（从第 N 轮派生新 Run，继承前史作为上下文，原 Run 归档不停机）、**ReplayTurn**（按原配置重执行该轮，其后续轮废弃——需在 Run 记录中注明）、**RollbackTurn**（回退到发送前状态，指令回填草稿）。操作均入 Issue 时间线。
- **衔接**：NG-B 失败策略的细粒度升级；与 MS-02 的 steer/jump 互补（干预在轮内，分叉在轮间）。
- **人日估算**：约 10 人日。

### MS-08 项目级配置随仓库版本化（P1）

- **MiraSim 机制**：`<workspace>/.mirasim` 目录承载工作区级技能与 schedules.json，**可随仓库提交**；全局技能与项目技能两级并存；`/` 一键列出全部可用技能。
- **Multica 痛点**：Skill 是平台侧配置，团队换库/新人入职要手工重配；NG-C 的 L1 显式技能层没有"随项目走"的载体。
- **建议改法**：定义 Multica 的项目级配置目录（如 `<repo>/.multica/`：skills/ + autopilot.json + workflows.json 省缺值），导入/同步命令一键入库；平台级配置仍全局生效，项目级覆盖同名项；快照与校验和入版本库，与 NG 的"开关化"灰度天然配合（工作区级开关文件就是项目级配置的一部分）。
- **人日估算**：约 3 人日（成本低、直接改善协作体验，建议尽早做）。

## 3. 不建议照搬清单

| # | 不照搬项 | 理由 |
|---|---|---|
| 1 | 把 Multica IDE 化（窗格/分组/TUI） | Multica 的用户是团队看板/飞书场景，不是开发者驾驶舱；做桌面工作台等于做第二个产品 |
| 2 | 平台额度/credits 商业模式 | Multica 是自托管开源，无平台计费面；只取其**账本口径**（MS-01），不取其计费 |
| 3 | 云端协作空间的运营形态（席位/观察位/地域限制） | 与自托管数据主权冲突；Multica 的 host 演进走"自管 Linux 服务器"路线即可 |
| 4 | 以"会话为中心"替换"任务为中心" | Multica 的组织价值在 Issue/Squad/Autopilot 流水线；会话级体验只借 Run 观测与干预能力 |
| 5 | 无跨会话语义记忆的现状 | 恰是 Multica 领先处：NG-C 的双层记忆（L1 技能 + L2 语义索引）应按原规划推进，不要被 MiraSim 的"无记忆"现状带偏 |

## 5. 与三阶段路线图的衔接

- **第一阶段（预算 + 工作流底座）**：MS-01 与 NG-A 同批交付（账本是闸门的观测面）；MS-08 作为快赢项穿插；MS-02 若资源允许在阶段末启动（daemon 心跳通道复用成本低）。
- **第二阶段（记忆 + 治理，工作流深化）**：MS-03 必须先于 NG-B fan-out 收敛落地（任务并行先要文件隔离）；MS-04 随 Squad 协议扩展同批；MS-05 观测环随 NG-C 装箱管线先行。
- **第三阶段（外部交接 + CI 护航）**：MS-06 补全 NG-F 复合质量门第四成员；MS-07 细化返工粒度。
- **验证口径不变**：每个 MS 项开关化后，第 2 册 LinkLite 例程必须原样重跑通过。

## 6. 结语

MiraSim 与 Multica 在光谱两端：前者把"人的即时操纵 + 会话并行 + 验收自动化"做到极致，后者把"组织任务流水线"做到极致。本文件取八件 MiraSim 验证过的零件（干预语义、worktree 隔离、通信熔断、账本口径、上下文观测、模拟用户、transcript 分叉、项目配置随库），以 MS-01~MS-08 编号挂接进 NG 六子域——总盘子约 67~72 人日，其中 MS-08 是性价比最高的快赢，MS-01 是第一阶段即可落地的观测刚需，MS-03/MS-06 分别补上 Multica 走向"多智能体真并行"与"无人值守真验收"的两块最后拼图。
