# Multica 审核改进计划：审批描述直白化 + 人工审核结论

> 定位：第 3 册《Multica改进架构设计书·Multica-NG》NG-D（治理审计审批）子域的**人机界面层专项展开**——不改审批逻辑与权限模型，只改"给审核人看的内容"与"审核人留下的结论"。
> 编号约定：新增登记项 **AR-01~AR-08**（Approval Readability），与 NG-A01~NG-X05、MS-01~MS-08 体系并行，可直接入看板。
> 现状基线：以本系列三册对 Multica 机制的核实为依据（看板人工验收、Issue 时间线记录、daemon 侧工具执行）；落地前请以实际部署版本界面复核，个别字段名以实测为准。

---

## 1. 背景与问题

Multica 的审核动作已经存在：看板列的人工验收、Issue 时间线的流转记录，以及 NG-D 规划中的 ApprovalGate 审批门（四挂接点：节点前置 / 预算联动 / 策略命中 / break-glass）。但**给审核人看的内容**始终是机器口径：

1. **审批描述技术化**：卡片上出现的是工具名、原始命令、参数 JSON、token 数。审核人要自己"翻译"——删的是什么目录？发布到哪？为什么花这些钱？判断成本高，误批与不敢批并存。
2. **审核结果不承载理由**：时间线只留一行"某某 approved at 14:32"。一个月后没人知道当时为什么放行、放行时有没有附加条件；复盘时无结论可查，审计时无依据可引。
3. **三类审核人各有困难**：业务审核人（不懂工具）看不懂；技术审核人（要拼细节）找不齐信息；管理者（要看结论）无结论可看。

**本计划回答两个问题：怎么把审批描述写直白；怎么让每次审核留下人可读、可查、可复盘的结论。**

## 2. 改进目标与原则

| # | 目标 | 判定口径 |
|---|---|---|
| G1 | 审批卡片"一句话可判断"：首屏即含全部决策要素，30 秒内可做出判断 | 抽检 10 张卡片，无"需打开折叠层才能判断"的情况 |
| G2 | 人工审核结论成为一等公民：每次审核留结构化结论（判定 + 理由 + 条件），可勾选、可检索、可复盘 | 试运行期结论覆盖率 ≥90% |
| G3 | 不破坏：现有审核点、权限、流程、账本全保留，只叠加"呈现层 + 结论层" | 关掉开关后页面回到原样（延续 NG 开关化原则） |
| G4 | 低成本落地：模板渲染 + 折叠 + 勾选短语为主，不引入新的重依赖 | 全计划约 40 人日（见第 6 节） |

**审批文案五军规**（所有卡片与结论共用）：

1. **一句话先行**：卡片首行回答"要批什么"，不看详情也能知道方向；
2. **一卡一问**：每张卡片只问一个决策问题，用"你要判断：……"句式收口；
3. **数字带语境**：金额带单位带余量（"¥0.3，预算剩 92%"），不裸放 token 数；
4. **风险独立成行**：级别 + 后果 + 可逆性三要素，不与正文混排；
5. **技术细节折叠**：原始命令、diff、参数默认收起，一键展开（证据还在，只是不挡路）。

## 3. 现状审核链路与呈现问题盘点

| 审核点 | 现在呈现的内容 | 审核人的困难 |
|---|---|---|
| 看板列验收（现状） | 列名 + 智能体产出物 + 时间线记录 | 上一步交付了什么、验收要点是什么，要自己翻 Issue 找 |
| Issue 时间线记录（现状） | 状态迁移 + 操作人 + 时间 | 只有"谁动了"，没有"为什么批"，事后不可追溯 |
| 工具调用确认（daemon 侧，现状） | 工具名 + 命令 + 参数 | 命令要逐词解读，风险靠人脑判断 |
| ApprovalGate 审批门（NG-D 落地后） | 挂接点 + 策略命中详情 | 若直接落机器口径，将把上述三类困难带入新链路 |

结论：直白化必须做在**渲染层**（对现状与新门禁同时生效），结论必须做成**新结构**（叠加在现有 approved/rejected 记录之上，不替换）。

## 4. 方案一：审批描述直白化（页面内容调整）

### 4.1 三层信息结构

每张审批卡片固定三层，默认展开前两层、折叠第三层：

```
┌ 第 1 层 结论层（默认展开）
│  一句话：要批什么（≤40 字）+ 风险级别标签
├ 第 2 层 决策层（默认展开）
│  它将执行（编号步骤） / 影响范围 / 预计花费与预算余量 / 你要判断
└ 第 3 层 证据层（默认折叠）
   原始命令 / 参数 JSON / 代码 diff / 策略命中详情 / 前序审核结论
```

### 4.2 审批卡片字段规范（生成侧强制）

审批请求提交时，人话字段**必填校验**，缺失即拒绝入队并要求补写（与 NG-B Submission 契约同款做法）：

| 字段 | 来源 | 规则 |
|---|---|---|
| summary | 智能体填 | ≤40 字，动宾结构，"把 X 正式发布到 Y"式 |
| steps | 智能体填 | 编号列表，≤5 步，每步一句人话 |
| risk | 智能体填，系统复核 | 级别（低/中/高）+ 后果 + 可逆性 |
| scope | 智能体填 | 影响范围：仓库 / 包 / 目录 / 工作区 |
| cost | 系统自动填 | 预计花费 + 预算余量百分比 |
| question | 模板按卡片类型生成 | "你要判断：……"单决策问题 |
| evidence | 系统自动附 | 原始命令、diff、参数（折叠层） |

### 4.3 三个改前 / 改后示例

**示例 1：工具调用审批（策略命中 ask）**

改前（机器口径）：

```

Tool: bash.exec
Args: {"command": "rm -rf build/ && npm run build && npm publish --access public"}

```

改后（人话优先）：

```

你要判断：这个版本号与内容是否允许对外发布？
▸ 原始命令 / 代码 diff / 前序评审结论（折叠）
```

**示例 2：预算审批（NG-A 预警联动）**

```
影响范围：若按当前速度跑完，月底预计超支 ¥12
你要判断：允许继续 / 暂停任务 / 申请上调预算？
▸ 预算明细 / 任务详情（折叠）
```

**示例 3：节点前置审批（ApprovalGate 节点挂接）**

改前：`workflow node 'deploy-prod' precondition gate pending, requires role: reviewer`

改后：

```
一句话：任务走到【发布上线】一步，按流程需人工放行。          [风险: 高]
前情摘要：单元测试 24/24 通过；代码评审 1 条意见已修复闭环
它将执行：将当前构建发布至生产环境
你要判断：是否放行上线？
▸ 测试报告 / 评审记录 / 构建 diff（折叠）
```

## 5. 方案二：人工审核结论（ReviewVerdict）

### 5.1 定位：叠加在现有审核结果之上

现有 approved/rejected 记录、审核人、时间戳**原样保留**；在其上增加一个结论对象。判定三值：**通过 / 驳回 / 有条件通过**（有条件通过必填生效条件，条件自动转为待办 Issue 挂回原审批卡，闭环前该 Issue 不可关闭）。

### 5.2 数据结构

```
ReviewVerdict
  verdict:        pass | reject | conditional-pass
  reasons:        [勾选项...]（来自短语库） + note（补充，限 200 字）
  condition:      生效条件（conditional-pass 必填）
  impact_note:    影响备注（可选，给下一个看到的人）
  reviewer / card_id / timestamp
  写后不可改：更正 = 追加一条更正结论；入 AuditLedger（NG-D 哈希链）
```

### 5.3 交互：勾选为主，3 击完成

结论面板 = 短语库勾选 + 少量补充。预置短语示例：

- 通过理由：命令与评审一致 ／ 版本号已核对 ／ 测试全绿 ／ 风险已知可控 ／ 前序结论已复核
- 驳回理由：版本号有误 ／ 评审意见未闭环 ／ 超出本次授权范围 ／ 风险未评估 ／ 与需求不符
- 常用条件：仅放行 beta ／ 本周内限一次 ／ 需产品二次确认

无结论的"通过"允许提交（不阻塞流程），但在复盘视图标灰提醒——用引导而非强制换覆盖率。

### 5.4 三个去向

1. **Issue 时间线**：单行呈现，任何人 5 秒读懂——"李四 · 通过 · 理由：版本号已核对、命令与评审一致 · 条件：仅放行 beta"；
2. **AuditLedger**：哈希链留痕，审计可引用；
3. **复盘视图**（AR-07）：按理由聚合，形成"驳回原因 TOP 榜"。

### 5.5 改前 / 改后

改前：时间线一行 `李四 approved RUN-882 at 14:32`——一个月后没人知道为什么放行。
改后：`李四 · 通过 · 理由：命令与评审一致、版本号已核对 · 条件：仅放行 beta · 备注：正式版需产品确认`——结论、边界、下游动作一眼可查。

## 6. 实施计划

### 6.1 三期排期

| 期 | 内容 | 登记项 | 人日 | 出口标准 |
|---|---|---|---|---|
| 第一期（第 1~2 周） | 卡片直白化 | AR-01~03 | 16 | 新卡片三端上线；旧审批记录兼容显示 |

| 编号 | 名称 | 优先级 | 人日 | 挂接 |
|---|---|---|---|---|

| AR-05 | 勾选式快捷理由短语库（预置 + 自定义） | P1 | 3 | NG-D |

合计 **40 人日**（16+14+10，复核无误）。优先级建议：AR-01~03 属"看板一上就受益"的呈现层改造，与 ApprovalGate 是否落地解耦，可先行。

### 6.3 灰度与兼容

- 按工作区开关灰度（延续 NG 开关化原则），关掉即回原页面；
- 无结论的旧审批记录不报错，复盘视图按"无结论"归档；
- 每期上线后按第 2 节四条目标口径抽检，未达标不入下一期；
- 第 2 册 LinkLite 例程须原样重跑通过（发布审批卡改后，例程验收步骤应更快走完）。

## 7. 验收标准

1. **30 秒可判断**：抽检 10 张在用卡片，首屏五要素齐（一句话 / 步骤 / 影响 / 花费 / 你要判断），无"必开折叠才能判断"；
2. **结论覆盖率 ≥90%**：正式试运行两周后统计（引导式达标，不设硬拦截）；
3. **误批率下降**：批准后 7 天内回滚或返工的审批占比，对比改进前基线（上线首月先测基线）；
4. **可追溯**：任取一条历史审批，5 秒内说出"谁批的、为什么、有没有条件"；
5. **兼容与回退**：开关关闭后页面回原样；LinkLite 例程重跑通过。

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| 智能体填的人话不准确（美化风险） | 术语翻译表兜底低风险卡模板；每周抽检 5 张人工复核；发现误导即入短语库负面清单 |
| 审核人懒得写结论 | 3 击完成（判定 + 勾理由 + 提交）；无结论仅标灰不拦截 |
| 结论自由文本变成垃圾场 | 短语库勾选为主，补充限 200 字 |
| 有条件通过的条件无人跟进 | 条件自动转待办 Issue，挂原审批卡，闭环前不可关 |
| 飞书端文案超长 | 五要素正文限 300 字，详情一律链接进 Web 端 |
