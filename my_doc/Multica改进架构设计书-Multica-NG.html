子域 A预算与成本治理P0

主要借鉴 Paperclip（按 agent 硬预算与熔断）、Claude Managed Agents（会话预算硬顶）
子域 B工作流运行时P0

主要借鉴 OpenAI Symphony（DAG 依赖 + 状态机）、「AI 军团」二次开发案例（Template/Node/Edge + Verdict）
子域 C记忆与上下文层P1

主要借鉴社区对 Multica 记忆模型的批评与 mem0 式上下文层思路
子域 D治理审计与审批P1

主要借鉴 Claude Managed Agents（auto 权限评估）、Paperclip（不可变审计日志与董事会治理）
子域 E外部系统交接P2

主要借鉴 OpenAI Symphony（watch CI / rebases / resolves conflicts / retries flaky）

01背景与动机：为什么改

Multica 已经证明了「agent 作为队友」的日常可用性。但当队列从每天几个任务变成上百个运行、从单智能体变成多小队并行时，四个结构性短板开始收税。

1.1 四大结构性短板

短板一：成本没有闭环。Multica 有用量看板（usage / analytics），能看历史消耗，但那是「事后会计」——没有任何对象表达「这个项目本月最多花多少钱」。对比赛道做法：Paperclip 给每个 agent 设月度美元预算，到 80% 预警、到 100% 自动暂停、新任务直接挡在门外；Claude Managed Agents 给每个会话设硬顶，触顶即停而非记账。Multica 目前缺的正是这条「事前闸门」，多智能体并行时尤其危险——失控循环一夜烧掉大量 token 的事故在社区里并不罕见。

短板二：工作流只有单线。现有 Workflows 的模型是「状态列 + 交接」：issue 进入某列触发一次交接，节点完成后「移至下一列」、被拒绝时「退回指定列」。这覆盖了线性交付，但表达不了三件越来越常见的事：并行（一个需求同时拆给后端 / 前端 / 测试用例三个智能体）、条件路由（按风险等级走不同评审深度）、结构化准出（下游只能读自然语言评论来判断上游成败）。OpenAI Symphony 的经验说明后者危害最大：当 agent 输出不稳定时，下游节点消费的应当是结构化裁定（pass / fail / blocked / rework），而不是再次推理一段散文。

短板三：记忆只显式、快照会过期。技能靠 agent_skill 显式挂载——精确、可控，这是 Multica 的优点，社区分析也证实「人工筛选的相关性往往优于统计相似」；但另一面是：未挂载的技能永远沉睡，任务执行中的新评论进不了已打包的上下文快照，且随着技能库增长（如 200 个技能），快照体积会持续膨胀。一线团队把这类问题总结为「缺乏模糊检索、快照过时、快照随库膨胀」三连。

短板四：治理是旁路而非内建。

Multica 有活动流（activity_log）与成员角色，但审计不是第一公民：没有防篡改的账本、没有可挂在敏感动作前的审批门禁、没有工具级权限策略。对比 Claude Managed Agents 的 auto 权限模式（服务器逐次评估每个工具调用：放行 / 拒绝 / 暂停等人批准）与 Paperclip 的 append-only 审计（每次工具调用、每个决策点都入不可变日志），「谁批准了这次超预算」「这个返工是谁驳回的」在现版本里只能靠翻评论拼。

1.4 非目标：明确不做什么

以下事项刻意排除在 Multica-NG 范围外
  • 不做模型训练与自研 CLI——继续复用现有 11 种 agent CLI 生态与 daemon 本地执行模型，算力与密钥留在用户机器上。
  • 不替换现有 UI 范式——看板、issue 时间线、收件箱交互保持；新概念以「详情面板 / 设置页扩展」形式出现。
  • 不动 Workspace 隔离模型——所有新表继续以 workspace 为界、级联删除，不引入跨工作区共享存储。
  • 不追求替代飞书 / 钉钉 / GitHub 专用集成——外部交接是通用底座，专用集成保留并逐步上移。
  • 不实现「无人值守自动合并」——所有 Verdict=pass 的产物仍需人工验收，这是 Multica「nothing ships without a human」的底线。

02现状基线与保留不动清单

改进的前提是精确理解现状。本章以 Multica 公开概念模型为基线，梳理执行链路与既有机制，并划出「坚决不动」的安全区——好的架构改进，一半靠加，一半靠忍住不加。

2.1 概念模型速览

Multica 的世界由四组对象构成：容器组——工作区（Workspace，一切的范围）与项目（Project，相关任务的聚合，可绑定仓库等资源）；执行组——智能体（Agent，可复用的配置：指令 / 模型 / skill / Access / 运行时）、Skill（可复用能力包，跨智能体共享）、运行时（Runtime，执行发生的电脑）与运行（Run，一次具体执行记录）；协作组——任务（Issue，日常工作单位，负责人可以是成员、智能体或小队）、小队（Squad，leader 智能体带领的多智能体协同）、对话与收件箱；自动化组——自动化（Autopilot，按时间表或外部事件触发执行）。触发方式有四条：分配、@提及、对话、自动化（现有 Workflows 的列交接本质上也是一种分配触发）。

2.2 执行链路与运行生命周期

一次典型执行的完整链路：触发 → 构建上下文快照（工作区上下文 + 任务 + 关联任务 + 挂载技能）→ 入队 → daemon 通过待处理队列轮询获取 → 调用对应 agent CLI 加载技能执行 → 过程中持续写回评论与状态（WebSocket 实时推送）→ 结果沉淀为可复用技能。运行（Run）本身经历一套完整状态机：

queued→dispatched→waiting_local_directory→running→completed/failed/cancelled

图 2-1 · 运行生命周期（简化）。每步状态转换都被跟踪并广播，无「无声失败」。

可靠性地毯包括：daemon 心跳（默认 15 秒级）、断线重连宽限（小时级）、每机并发上限（agent 级与整机级双层）、临时错误的自动重试与网络错误的更高次数重试、以及自动化熔断（7 天内失败次数与失败率双阈值触发暂停）。这些机制在 P0 两个子域中全部复用，不改一行语义。

2.3 协作机制：小队与任务阶段

小队协议是 Multica 最精巧的现有设计：leader 智能体收到任务后向成员发出简报（Squad Operating Protocol + 名单 + 指令），以 @成员 方式派活；成员完成后不带 @ 地回复（静默汇报，避免互相唤醒）；只有显式 @leader 才把队长拉回。任务阶段机制则实现了「级联唤醒」：一个任务的各阶段（phase）依次完成，最早未完成阶段全部 done 时，系统自动唤醒父任务负责人。这两个机制天然就是「有向图运行时」的雏形——本设计的子域 B 不是替换它们，而是把这套隐式协议升级为显式声明式模板。

2.5 保留不动清单（安全区）

以下机制在 Multica-NG 中保持原样，任何子域不得破坏其语义
  • Workspace 隔离与级联删除——所有新增概念继续以工作区为界，删工作区即净身出户。
  • Daemon + Runtime 本地执行模型——算力、密钥、代码目录留在用户电脑；NG 的新检查点全部是「派发前置」而非「远程执行」。
  • 11 种 agent CLI 自动检测——厂商中立是立身之本，新子域不得引入对特定 CLI 的硬依赖。
  • Squad 协作协议——leader / 静默汇报 / 让位规则原样保留，并可作为子域 B 中的「协作节点」整体入图。
  • Issue 时间线与评论模型——所有新事件的呈现都写回时间线，不另立消息中心。
  • Autopilot 触发器——保留为工作流的合法触发源之一（定时 / 外部事件 → 启动图实例）。
  • 飞书 / 钉钉 / GitHub 集成与长连接事件——通知面不动；子域 E 只增加通用 Hook 底座。
  • 自托管部署面——延续第 1 册验证的 make selfhost 与就绪检查路径，新子域全部默认关闭、按需开启。
为什么「不动」是设计决策而非偷懒：一线二次开发案例的教训清单里，「快照可能过时」「缺乏跨工作区记忆」等短板全部源自早期侵入式改动。叠加式演进让每一步都可以独立回滚（第 11 章），也让 upstream 升级冲突面最小（第 12 章风险 R5）。

3.1 演进三原则

原则一 · 插件化

六大子域各自是可插拔模块：预算可以只开 A 不开 B，治理可以只开账本不开审批。全部关闭时系统行为与现状逐字节一致。「关掉等于没改过」是回归测试的黄金标准。

原则二 · 开关化

每个子域一个特性开关（feature flag），支持按工作区灰度：先开一个试点工作区跑影子模式，对比无异常后再全量。开关状态本身入审计账本。

原则三 · 不破坏

新概念一律以「引用」方式挂接旧对象，而非替代：StepInstance 引用 Issue 而非取而代之，Budget 挂在 Agent/Project 之上而非改造它们。旧数据永不迁移删除。

贯穿原则 · 事件化

一切状态变化都是事件：成本是事件、裁定是事件、审批是事件、交接是事件。审计与指标是同一事件流的两种消费，不搞两套采集。

4.4 与现有 analytics 的关系

现有用量看板回答「过去花了多少」，Budget 回答「还允许花多少」；两者共享同一 CostEvent 事件流——看板是事件流的回放视角，预算是事件流的前馈控制。实现上不再另做采集：CLI 上报的用量数据落成 CostEvent 后，一边进看板聚合、一边累加进 QuotaSnapshot。历史 usage 数据建议回填为 CostEvent（第 11 章），使预算基线可以从真实历史学习出「同类任务 P50 成本」。

4.5 场景走查：LinkLite 例程中的预算护栏

走查：L7 鉴权限流任务触发熔断并恢复的全过程

沿用第 2 册例程：某月项目「LinkLite」预算 200 美元，智能体 Backend 月度子预算 80 美元。L7（鉴权与限流）任务预估 6 美元。

  1. 月初任务逐个完成，CostEvent 累计 Backend 已用 77.2 美元 → 触发 80% 预警（61.4 美元线已过），收件箱与飞书群收到预警通知，任务照常。
  2. L8（e2e 测试）入队时预估 4 美元：77.2 + 4 < 80，放行并预扣 4 美元；运行完成后实际 3.1 美元，冲抵退回 0.9 美元。
  3. L9（部署文档）预估 3 美元：77.2 + 3.1 + 3 < 80，放行。但该任务实际跑了 2.4 美元后进入一个修复循环，核销时累计达 82.7 美元 → 熔断。
  4. 此后队长试图派发新子任务，入队闸拒绝并附明细（预估 5 美元 vs 剩余 -2.7 美元）；helper 管家智能体收到事件，在 issue 时间线留下熔断说明。
  5. 负责人判断循环属正常返工，将 Backend 子预算提至 100 美元 → ApprovalGate 向工作区 admin 发审批（收件箱直达，一键批准）→ 审批入审计账本 → 熔断解除，排队任务恢复派发。

验收口径（对应 G1）：全程没有任何一笔「无预算管辖」的运行；熔断到恢复的每个动作（拒绝、通知、提额、批准）在审计账本中单查询可得。

4.6 设计边界与已知取舍

  • 计量误差：本地执行的 token 用量依赖 CLI 上报，允许 5% 容差缓冲（预警线默认 80% 而非 95% 即为此留白）；预留-核销机制吸收并发透支。
  • 故障降级：预算服务不可用时fail-closed（暂停派发而非放行）——宁可停也不失控；该决策入第 10 章演练清单。
  • 不做的事：不做跨工作区合并预算、不做实时汇率折算（费用按配置的固定单价表折算）、不做按模型退避降价建议——那是运营工具，不是架构。

5.5 与现有机制的接缝

  • Issue 不变：每个 agent / human / squad 节点激活时创建或复用 Issue——看板、评论、@提及、收件箱全部原样工作。
  • Squad 作为协作节点：小队整体入图时，内部 leader 协议、静默汇报、让位规则不变；小队对外的完成汇报落成一份 Submission。
  • Autopilot 作为触发器：定时 / 外部事件触发「启动图实例」，替代原本只能触发单次执行的限制。
  • 现有 Workflow 导入：线性列模板一键转为「节点-边」线性图（列 = 节点，交接 = 边，「完成后移至 / 退回」= 默认边 / 返工边），导入后可增量添加并行与网关。
  • 阶段机制兼容：现有任务阶段唤醒继续工作；图中节点完成即阶段 done，父级唤醒逻辑复用。

5.6 设计边界

  • 不做通用工作流引擎：不做循环边、不做动态图（运行中改拓扑）；需要循环的场景用 subworkflow + 显式重试表达。Symphony 的教训：把 agent 当刚性状态机节点会浪费其推理能力，因此节点给的是「目标 + 准出条件」，不是脚本步骤。
  • 不做跨工作区模板共享：模板以工作区为单位；受控导出 / 导入留作运营功能。
  • Verdict 不裁决业务对错：裁定只回答「这一步是否达到其声明的准出条件」；业务对错永远由人工验收节点（或集成层的外部验收）说了算。

针对「快照一次性、执行中新评论进不来」的批评，设计一条轻量增量通道：运行期间，任务上的新评论、blocked 标记、验收驳回以 IncrementalEvent 追加到该 Run 的待注入队列；daemon 心跳节拍上顺带投递（复用现有心跳，不新增连接）。智能体侧表现为会话中出现一条带时间戳的系统注入消息——不重建快照、不打断执行。对长任务（小时级）这是「保鲜」与「稳态」的折中：重大上下文变化（如任务被改派）仍走取消重启，不强行热更。

6.4 快照体积控制

技能库增长带来的快照膨胀（200 个技能即很大的上下文块）由管线「装箱」环节统一解决：L1 挂载项与 L2 召回项在同一个 token 预算内竞逐，超预算时按（相关度 × 新鲜度 × 是否显式挂载）排序截断，被截断项以「可按需引用的索引行」形式保留占位（智能体可通过工具调用按需拉取全文）。由此，快照体积从「随库增长」变为「恒定预算 + 按需展开」。

6.5 设计边界

  • 不做跨工作区记忆：L2 索引严格按 workspace 分片；「技能市场」式受控导出 / 导入属运营功能，不在架构范围。
  • 检索不覆盖挂载：L2 召回永不挤占 L1 显式挂载项的预算份额——显式优先是硬规则。
  • 隐私红线：过滤环节对密钥、凭据模式做硬脱敏；L2 索引内容与权限模型联动（无权限对象不进召回候选）。
  • 可降级：语义层故障时管线自动退化为「仅 L1」模式——记忆层失效不应导致任务无法派发。

D子域 D · 治理、审计与审批 P1

目标 G4：关键动作可审计、不可篡改、可追溯；敏感动作发生前有门禁。三个组件：审计账本（事后可查）、审批门禁（事前拦截）、工具策略（事中评估），全部挂在第 3 章的治理层。

7.1 审计账本 AuditLedger

现有活动流是「给人看的展示层」；AuditLedger 是「给制度看的存储层」——append-only 事件账本，每条记录含：动作主体（人 / 智能体 / 系统）、动作客体、前后状态摘要、trace_id（贯穿一次图实例的追踪键）、以及前一条记录的哈希，形成哈希链：任何历史篡改都会破坏链校验。必录动作清单：预算变更与熔断 / 恢复、审批的发起与裁定、Verdict 落账、返工裁决、外部交接收发、工具策略的 auto 裁决、特性开关切换。查询场景即验收口径：「谁批准了这次超预算」「这个返工是谁驳回的」「这周哪些 auto 裁决拒绝了什么工具调用」都应是单查询可得。

7.5 设计边界

  • 账本不存密文大对象：只存动作与状态摘要，附件引用原始对象——账本膨胀会拖垮哈希链校验性能。
  • 审批超时策略：默认「一直等」（保守），模板可配超时自动驳回——自动通过永远不是可配项，这是安全底线。
  • 不做多层组织树审批流：单人门禁 + break-glass；若组织需要多级审批，那是子域 E 从外部系统接入的流程，不在平台内复制。

E子域 E · 外部系统交接 P2

目标 G5：真实工作不必搬进平台——外部系统（需求 / 缺陷 / 验收 / 发布）在合适的状态把工作推给 Multica，Multica 组织智能体执行，再把结果与状态交回去。三条铁律：幂等、重放、对账。

8.2 三机制：幂等、重放、对账

  • 幂等：入站事件以「外部 ID + 事件序号」为幂等键，重复投递不产生第二个图实例；出站回写携带唯一事件 ID，外部系统可安全去重。
  • 重放：出站失败按退避重投递，超过阈值进死信队列并告警；死信支持人工修复后重放——交接不丢。
  • 对账：低频周期任务（Autopilot 驱动）拉取外部状态与平台状态比对，漂移项生成对账报告 + 单向修正建议——机器只建议，人确认修正。

8.3 与现有集成的关系

飞书 / 钉钉 / GitHub 集成原样保留。子域 E 是通用底座：专用集成未来可逐个上移为「InboundHook 的适配器」（例如 GitHub issue 事件 → template_key=bugfix 的图实例），但这是演进选项而非要求——底座与专用集成长期共存，谁好用用谁。

8.4 设计边界

  • 不代管外部状态：平台永不直接修改外部系统的业务字段，只回写「执行侧事实」（完成 / 失败 / 待验收 + 证据链接）。
  • 验签是硬门槛：入站无签名验证直接丢弃并计数告警——开放端点必须默认敌意。
  • 对账不自动修正：漂移修正永远人工确认（与「不无人合并」同一底线）。

F子域 F · CI 护航 P2

目标 G6：Symphony 的观察值得原样引用——大仓库里 PR 的最后一公里又慢又脆，系统应当「看着 CI、按需 rebase、解冲突、重试 flaky、护送变更进主分支」。本子域把这件事变成 Multica 的一个执行层旁路：专职守护智能体（Guardian）+ Verdict 质量门。

9.2 Guardian 智能体与护栏

Guardian 不需要新执行机制：它是普通智能体配置 + 一组专用 skill（读 CI 日志、评估冲突复杂度、执行 rebase），由图模板中的「交付前置节点」自动唤起。护栏三件套：限速（每 PR 每小时干预次数上限，防守护自身打转）；权限最小化（ToolPolicy 默认 deny push main，仅允许维护 PR 分支）；全程入账（每次重试 / rebase / 派回都以事件入审计账本）。合并动作永远留给人工——守护止步于「待合并」。

9.3 与 Verdict 质量门的联动

交付节点的准出条件升级为复合门：Verdict == pass（业务裁定）且 CI 守护状态 == 待合并（工程裁定）且（可选）外部验收 == approved（集成层裁定）。三门全绿才进入人工合并确认——「到合并时已高度确信能进主分支」正是 Symphony 报告的效果，NG 不需要新机制即可继承。

9.4 设计边界

  • 只守护，不合并：自动合并明确排除（第 1 章非目标重申）。
  • 不绑定特定 CI：检查状态抽象为「外部检查源」，GitHub Checks / 内部流水线通过集成层适配。
  • flaky 判定保守：仅对「同 commit 重跑变绿」标记 flaky；其余一律按真失败派回——宁可多派回，不可漏放行。
