## 二、关键决策：容器化 vs 源码安装

**结论：Ubuntu 上部署选容器化（Docker Compose 自托管），源码安装只用于开发/贡献代码。**

| 维度 | 容器化 `make selfhost` | 源码安装（Manual Setup without Docker） |
| --- | --- | --- |
| 依赖 | 只需 Docker + Compose | Go 1.26.9 + Node.js 22 + pnpm 10.28.2 + PostgreSQL 17 全自备 |
| 启动 | 一条命令，自动建 `.env`、生成 `JWT_SECRET`、拉镜像起服务 | 手动建库、跑迁移、分别构建前后端 |
| 升级 | `pull && up -d`，迁移自动执行 | `git pull` + 重新构建 + 手动迁移 |
| 适用 | 正式部署、日常自托管 | 开发调试、无 Docker 权限 |

### 三条 make 命令的本质区别

```
代码 → 服务的两条路径：
  ① 拉现成镜像：GHCR 官方仓库 --pull--> Docker 容器（不含本地改动）
  ② 源码现场构建：本地源码 --build--> 本地镜像 --> Docker 容器（含本地改动）
  两条路径最终都是 Docker 容器在跑，区别只在镜像来源。
```

| 命令 | 镜像来源 | 用途 |
| --- | --- | --- |
| `make selfhost` | GHCR 拉官方预构建镜像（`:latest`） | 正常部署 |
| `make selfhost-build` | 从当前 checkout 构建 `multica-backend:dev` / `multica-web:dev`（不覆盖 `:latest`） | 想跑自己改过的源码，但保持容器化管理；或 GHCR 标签未发布时兜底 |
| `make dev` | 不建镜像，宿主机起开发服务（热更新、开发配置） | **写代码调试用，不能当部署** |

一句话：**部署形态永远是容器；镜像来源决定选哪条命令。**

## 三、账号与登录

- Multica **没有账号+密码，也没有预置管理员账号**；用「邮箱 + 验证码」登录。
- **第一个注册并创建工作区的用户自动成为 `owner`**（角色 `owner` / `admin` / `member`）。
- 三种取码方式：① `.env` 配 `RESEND_API_KEY` 发真实邮件（生产推荐）；② 不配邮件时看后端容器日志 `[DEV] Verification code for ...:`；③ `APP_ENV=development` + `MULTICA_DEV_VERIFICATION_CODE=888888`（仅本地测试，**公网禁用**）。

```bash
docker compose -f docker-compose.selfhost.yml logs -f backend | grep "Verification code"
```

本次实测验证码日志：`[DEV] Verification code for huasheng_zyh@163.com: 459994`。

## 四、运行时连接：桌面端不是必需的

Web 界面提示「连接一台电脑来运行你的智能体」时，**不需要安装桌面端**。桌面端只是把「注册本机为运行时 + 扫描已装智能体 CLI」这一步自动化；真正必需的是 **`multica` CLI + 守护进程（daemon）** 跑在某台机器上。

| 方式 | 操作 |
| --- | --- |
| 桌面端 | 安装即自动注册本机 |
| **网页版 + 命令（本次采用）** | 团队 → 运行时 → 添加运行时 → 其他机器或服务器 → 执行弹窗给的两条命令 |
| 纯终端 | `multica setup`（登录+注册+启动 daemon） |

Web 页面「实时 · 正在等待你的电脑」的含义：服务端轮询等待一个用你身份注册的守护进程；它不会自己失败，做完 CLI 步骤就会自动连上。

## 五、本次实操全过程（含排障）

### 1. 服务端已由容器跑起来

- `make selfhost` 起 Docker Compose 栈；实测 `127.0.0.1:8080`（后端）与 `127.0.0.1:3000`（前端）均在 LISTEN。
- 容器部署**只包含前端/后端/数据库**；宿主机 CLI 与守护进程要另外装。

### 2. 首次检查：CLI 与 codebuddy 均缺失

```
multica: command not found
which codebuddy → 无；npm 全局包无 codebuddy；~/.codebuddy/bin 无
PATH 中的 tencent-cloud.coding-copilot 是 CodeBuddy IDE 插件 shim，不是独立 CLI
~/.local/bin 下有 claude
```

### 3. 安装 multica CLI（网络坑）

| 尝试 | 结果 |
| --- | --- |
| `curl ... raw.githubusercontent.com/.../install.sh \| bash` | SSL 连接超时（被墙） |
| GitHub Releases 直连下载 | 后台 curl 中断，包截断在 2.24MB，`tar` 报 `unexpected end of file` |
| **镜像 `https://ghfast.top/` + GitHub Releases 路径** | ✅ 一次成功，完整包 7,893,832 B（v0.8.0） |
| `sudo mv /usr/local/bin` | 失败：sudo 需要密码、无 tty |
| **改装 `~/.local/bin`（PATH 首位）** | ✅ `multica 0.8.0 (commit 9b1ab4f9e, built 2026-11-03)` |

```bash
URL="https://github.com/multica-ai/multica/releases/download/v0.8.0/multica-cli-0.8.0-linux-amd64.tar.gz"
curl -sL --connect-timeout 10 --max-time 120 "https://ghfast.top/${URL}" -o /tmp/multica.tar.gz
tar -xzf /tmp/multica.tar.gz -C /tmp multica
mv /tmp/multica ~/.local/bin/multica && chmod +x ~/.local/bin/multica
multica version
```

### 4. 安装 codebuddy CLI（Node 版本坑）

```bash
npm install -g --prefix=$HOME/.local @tencent-ai/codebuddy-code   # 11 包，28s
```

- `codebuddy --version` 首次报 `requires Node.js v18.20.8 or newer`；系统 `/usr/bin/node` 是 **v18.19.1**，nvm 里已有 **v20.20.2**。
- 修复：`source ~/.nvm/nvm.sh && nvm alias default 20.20.2` → `codebuddy 2.177.1` 正常。
- 登录态：`~/.codebuddy/config.json` 中 `apiKey` 已存在（只校验不回显密钥），无需重新登录。

### 5. `multica setup self-host`（认证坑）

第一次后台启动：

```
nohup multica setup self-host --server-url http://localhost:8080 --app-url http://localhost:3000 &
→ 打开浏览器等待授权，回调端口 localhost:36835
→ 用户点「授权」时浏览器报 ERR_CONNECTION_REFUSED
→ 原因：setup 等待认证「timed out waiting for authentication」自动退出，回调端口随之关闭
```

第二次重跑（新链接、新端口 33057），且配置重置需要交互确认，用管道自动应答 `y`：

```bash
nohup bash -c 'echo y | multica setup self-host --server-url http://localhost:8080 --app-url http://localhost:3000' > /tmp/multica_setup2.log 2>&1 &
```

这次在超时窗口内用户浏览器授权生效：

```
Authenticated as huasheng_zyh (huasheng_zyh@163.com)
Token saved to config.
Found 1 workspace(s): scc-at (5ad87c98-8ec6-46a5-bd49-a5c017b851d6)
Daemon started (pid 2902548, version 0.8.0)
✓ Setup complete! Your machine is now connected to Multica.
```

> 授权链接里的 `cli_state` 与回调端口是一次性的；过期/被拒就重跑 setup 生成新链接，并**尽快**点授权。

## 七、codebuddy 模型配置

三种方式：

| 方式 | 命令/位置 | 生效范围 |
| --- | --- | --- |
| 会话内 | 交互式输入 `/model` | 当前会话 |
| 命令行参数 | `codebuddy --model glm-5.3 -p "任务"` | 单次运行 |
| **持久化** | `codebuddy config set -g model <id>` 或 `~/.codebuddy/settings.json` | **全局，Multica 场景必须用这种** |

关键点：**Multica daemon 后台拉起 codebuddy 时既不带 `--model` 也没有交互会话**，所以 Multica 里跑的模型完全由持久化配置决定；改完不用重启 daemon（每次任务都是新进程）。

本次已在 `~/.codebuddy/settings.json` 首位新增（其余 `trustedDirectories`、`enabledPlugins` 原样保留）：

```json
{
  "model": "glm-5.3-flash",
  ...
}
```

验证：`codebuddy config get model` → `glm-5.3-flash`。

可用模型 ID（`codebuddy --help` 实测，v2.177.1）：

| 系列 | 模型 ID |
| --- | --- |
| CodeBuddy 自研（混元） | `hy4free` `hy4std` `hy3` `hy3-x` |
| 智谱 GLM | `glm-5.3` `glm-5.3-flash` `glm-5.3-flashx` `glm-5.2` |
| DeepSeek | `deepseek-v4.1-flash` `deepseek-v4-pro` |
| Kimi | `kimi-k3.1-pro-highspeed` `kimi-k3.1-pro` `kimi-k3-2` `kimi-k2.8-preview` |
| MiniMax | `minimax-m3.1-flash` `minimax-m3-pay` `minimax-m2.7` |
| 其他 | `space-bunny` `step-5-preview` `mimo-v2.6-pro` |

建议：Multica 日常批量任务用 flash 档（成本/延迟优），复杂重构再切强模型。

## 八、坑与经验教训汇总

1. `raw.githubusercontent.com` 在本机 SSL 超时；GitHub Releases 直连也会中途断链（下载后必须 `tar -tzf` 校验完整性）；**镜像前缀 `https://ghfast.top/` 可直接拼在原始 GitHub URL 前**。
2. `sudo` 在无 tty 的会话里需要密码会失败 → 用户级 `~/.local/bin`（PATH 首位）是更省事的安装位置。
3. 容器部署只起服务端三件套，**CLI + daemon 必须另外在宿主机装**，否则 Web 会一直「等待你的电脑」。
4. CodeBuddy IDE 插件 ≠ 独立 `codebuddy` CLI；daemon 只扫描 PATH 上的可执行命令。
5. codebuddy CLI 要求 Node ≥ 18.20.8；系统 node 18.19.1 差一个补丁版，用 nvm 已有 v20 设默认即可（daemon 需继承该 PATH）。
6. `multica setup` 的浏览器授权**有超时**；超时后回调端口关闭，浏览器回跳必 `ERR_CONNECTION_REFUSED` → 重跑并尽快批准；重复运行时会问「重置配置？[y/N]」，非交互环境要 `echo y |`。
7. 无浏览器/headless 环境的替代：`multica login --token <mul_...>`（令牌在 Web Settings → Tokens 生成）。
8. 自托管服务端默认每 UTC 日发一份部署级匿名快照；不想发就在 API 服务端设 `DO_NOT_TRACK=1` 后重启（`ANALYTICS_DISABLED` 管不到这套）。
9. 公网实例**禁止**设置 `MULTICA_DEV_VERIFICATION_CODE`，否则任何知道邮箱的人都能登录。

```bash
# 服务端（容器）
make selfhost                                        # 启动

docker compose -f docker-compose.selfhost.yml pull && \

# CLI / daemon（宿主机）
multica version

multica auth status
multica daemon status
multica daemon logs -f
multica daemon stop && multica daemon start          # 重新扫描智能体 CLI
multica daemon autostart enable                     # 登录自启（建议）

# codebuddy
source ~/.nvm/nvm.sh && nvm use 20.20.2              # Node ≥ 18.20.8
codebuddy --version
codebuddy config get model
codebuddy config set -g model glm-5.3-flash
```
